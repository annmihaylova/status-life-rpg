## 2. Что в SPEC противоречиво или не определено

Предлагаю решения, их можно поправить.

1. **Пересчёт требует журнала решений, а не только XP.** `pnpm game:recompute` не восстановит состояние только из `activity_entries`: результат зависит от решений пользователя (взяла навык, раскрыла характеристику, калибровка, перенос слота, выбор специализации, пробуждение). Предлагаю таблицу `game_decisions` (user_id, kind, payload, decided_at), и движок как чистая функция `replay(entries, decisions, config) → state`. Агрегаты в БД остаются кэшем.
2. **Порядок убывающей отдачи внутри дня.** Какая запись получает ×1.0, а какая ×0.7, зависит от порядка. Предлагаю сортировку по `started_at`, затем `created_at`. Тогда пересчёт детерминирован.
3. **novelty 1.25 в примере MCP (7.3)**, а в 3.1 допустимы 0.9 / 1.0 / 1.2. Предлагаю непрерывный диапазон 0.9–1.2 с обрезкой, intensity — 0.5–1.6.
4. **Узкие навыки из примеров убираем (решено).** «Анализ белковых интерфейсов» и «Чтение научных статей» навыками не будут. Вместо фиксированного каталога навыки появляются автоматически под человека, см. раздел 2а. Титул «Пожиратель статей» считается по навыку вроде «Книжного червя».
5. **«Интеллект (Логика)» в 2.7.** Характеристики «Логика» нет. Класс «Инженер» = Интеллект + Творчество.
6. **«День отдыха», «Второе дыхание», вес XP без навыка (решено: пробуем разные варианты).** Это переключаемые эксперименты, см. раздел 2б. Для отдыха у навыка и записи появляется флаг `is_rest`, он же нужен HP для восстановления (+5% за 30 минут).
7. **Drizzle и RLS.** Серверное подключение Drizzle к Postgres по умолчанию обходит RLS. Все пользовательские запросы пойдут через обёртку `withUser(userId, tx => …)`: `set local role authenticated` и `request.jwt.claims` в транзакции. Тогда RLS действует и на сервере, а тест RLS проверяет обе стороны.
8. **Статический заголовок для custom connector в Claude (7.2).** Не уверена, что Claude сейчас позволяет задать произвольный заголовок. Проверю по документации в начале фазы 2. Запасной вариант: сразу минимальный OAuth 2.1 через готовую библиотеку, то есть часть фазы 5 переедет в фазу 2.

## 2а. Навыки появляются автоматически

Решение после обсуждения 2026-11-26: заранее прописанный список навыков всех людей не покроет, поэтому Система подбирает навыки под человека сама. Список в `presets.json` — только примеры для LLM, а не ограничение.

**Навык — это умение, а не тема.** Можно называть его в духе LitRPG, если название понятное: «Книжный червь» качается от чтения сложных, непонятных текстов, неважно, статья это по биологии, учебник или философия. Остаются и предметные навыки («Биология», «Программирование»). Нельзя: задачу, курс, проект, инструмент («домашка», «BIO120», «PRODIGY», «Python»).

**У навыка два поля:**
- `name` — как он показан в окне статуса: «Книжный червь».
- `scope` — что в него засчитывается, одной-двумя фразами: «чтение сложных текстов, где приходится разбираться: научные статьи, учебники, документация, плотная нон-фикшн».

Классификатор (чек-ин и MCP) распределяет записи по `scope`, а не по названию. Поэтому необычные названия не мешают точности. Пользователь может поменять и то и другое.

**Как это работает:**
1. Запись, которая не подошла ни под один навык, получает от LLM короткое описание умения (`activity_cluster`) и попадает в кандидаты.
2. Новые кластеры сравниваются с уже существующими кандидатами и навыками пользователя (LLM-сравнение по `scope`, позже эмбеддинги). Похожее склеивается, чтобы «читала статью про белки» и «разбиралась в учебнике» копились в одного кандидата.
3. Когда кандидат набрал порог (≥ 120 минут, ≥ 2 дня за 14 дней), LLM предлагает итоговые `name`, `scope`, теги характеристик и `is_work_shift`, а Система показывает предложение «Доступен навык». Опыт засчитывается задним числом.
4. Одна запись может кормить до 3 навыков с долями: чтение сложной статьи по биологии → «Биология» 0.6 + «Книжный червь» 0.4.
5. Защита от мусора: серверная проверка названия (не курс, не задача, не инструмент; есть стоп-список и повторный вопрос к LLM) и лимит 1–2 новых предложения в неделю, чтобы навыки не сыпались горой.

Позже (фаза 5), когда пользователей станет много, из удачных навыков сложится общий каталог. Он поможет предлагать устоявшиеся названия, но навыки по-прежнему будут создаваться под человека.

## 2б. Эксперименты

Правила, в которых пока нет уверенности, вынесены в конфиг как варианты. Переключатель — в Settings → «Эксперименты» (видно только тебе, пока продукт личный). При смене варианта история пересчитывается через `replay()`, так что можно сравнивать на своих же данных.

| Правило | Вариант A (по умолчанию) | Вариант B | Вариант C |
|---|---|---|---|
| День отдыха → бафф «Восстановление» | за день < 120 мин фокуса вне отдыха и ≥ 60 мин отдыха | только если сама отметила «сегодня отдыхала» в чек-ине | LLM решает по вечернему отчёту |
| «Второе дыхание» после перерыва ≥ 7 дней | +10% XP персонажа в первый день после перерыва | +20% XP навыков на 3 дня | только сообщение и титул «Возвращение», без бонуса |
| Вес XP характеристик от активности без навыка | ×0.5 | ×1.0 | ×0.25 |

Ручная отметка «сегодня отдыхала» засчитывается во всех вариантах. Варианты и их параметры — в `lib/game/config.ts`, выбранный вариант хранится в `user_settings.experiments`.

## 3. Фазы

Каждая фаза заканчивается деплоем на Vercel, зелёным CI и обновлённым `CLAUDE.md`.

### Фаза 0 — фундамент
- pnpm (через corepack), Next.js App Router + TypeScript strict, Tailwind + shadcn/ui, next-intl (ru по умолчанию, en), ESLint + Prettier.
- Supabase: Auth (magic link + Google), Drizzle-схема всех таблиц раздела 10 плюс `game_decisions`, RLS-политики в миграциях, тест RLS на каждую таблицу. Локально — Supabase CLI в Docker (Docker установлен), прод — облачный проект.
- `lib/game/`: `config.ts`, `formulas.ts` (`FORMULA_VERSION = 1`): XP записи, убывающая отдача (включая `is_work_shift`), уровни персонажа и навыков, ранги, слоты, очки и звёзды характеристик, `days_required`, раскрытие, `computeHp`. Тесты сверяют таблицы выше и пример раскрытия, TS-порт `simulate` сверяется с выводом `balance.py`.
- GitHub Actions: lint, typecheck, vitest. Пустое приложение задеплоено на Vercel. `.env.example`.

### Фаза 1 — MVP «для себя» (три деплоя)
- **1a. Движок:** `replay()` по записям и решениям, леджер `xp_events`, `pnpm game:recompute` (тест: пересчёт = инкрементальный результат), кандидаты навыков (≥ 120 мин, ≥ 2 дня за 14 дней) с ретро-зачётом, спящие навыки (×5 до цели, с разбиением записи на границе), слоты и архив, звёзды, очки, раскрытие, калибровки, специализации, HP и статус-эффекты, варианты-эксперименты из 2б, генератор системных сообщений.
- **1b. Интерфейс:** онбординг (5 экранов → спящие навыки → стартовые навыки → оценка и калибровка → имя), Status, Skills, Journal, ручной лог за 3 тапа, системные сообщения с анимацией, 2D-портрет-заглушка. Конфиги `attributes.json`, `presets.json`, черновики классов и титулов (вопрос 14.5).
- **1c. Чек-ин текстом:** серверный вызов Anthropic API (модель в конфиге), structured output через tool use, zod-валидация и нормализация долей, карточки-черновики (подтвердить / поправить / разделить / удалить / «подтвердить всё»), `merge_with`. E2E на фикстуре из раздела 8, месячный лимит LLM-вызовов.

### Фаза 2 — ИИ-агент
MCP server на `/api/mcp` (Streamable HTTP, официальный SDK), токены в Settings (хэш, отзыв), все 7 инструментов, идемпотентность `client_ref + date`, rate limit 60/мин, экранирование описаний в ответах, инструкции подключения к Claude и ChatGPT, интеграционные тесты и MCP Inspector.

### Фаза 3 — привычка
PWA и service worker, web push (VAPID) с инструкцией для iOS, email-запасной канал (Resend), cron каждые 15 минут по локальному времени, таймер, запись голоса и speech-to-text (сравню 2 сервиса по цене и качеству русского), Chronicle (сравнения, итоги, heatmap, письмо Системы), титулы, классы.

### Фаза 4 — персонаж
VRM: 4a базовые модели и материалы с `LICENSES.md`, 4b импорт своего `.vrm`, 4c косметика. PNG-fallback.

### Фаза 5 — для других
OAuth 2.1 для MCP с refresh tokens, лимиты, лендинг, экспорт и удаление аккаунта, аналитика без содержимого.

### Фаза 6 — приложение
Capacitor или Expo — решаем после фазы 5.
